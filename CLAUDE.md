# TagFox

Electron desktop UI over the local [Voidtools Everything](https://www.voidtools.com/) HTTP server. No backend; it talks only to Everything and the local filesystem. Main editor: Cursor.

Role: the tool Steve reaches for a hundred times a day, so it has to work in his hands rather than in a test. Measure what is on screen before designing for it; land the work on `main` in `C:\dev\TagFox`, where he runs it; prove it in the running app before calling it done. Ledger: `_role.md`.

## Working rules

- **A background job here runs directly in `C:\dev\TagFox`, not an isolated worktree** (`.claude/settings.json` sets `worktree.bgIsolation: none`). A fresh worktree carries no `node_modules`, so a job confined to one could edit but never run `npm test` or `npm run dist`, and the result has to land in this checkout anyway since it's where Steve runs the app. See memory `[[background-jobs-and-worktrees]]` for the general rule and the escape hatch.
- **Steve runs TagFox with `npm start`, always. He never installs the packaged app.** So `npm run dist` exists only to hand Gabriele a build (the installer is copied to the Causal Map Drive root by `scripts/run-dist.js`); build it when asked to ship, and never install or update an exe on Steve's machine. When diagnosing his running app, it is the working tree, not a packaged build. A second running instance is another `npm start`, which loses the global hotkeys and the Chromium disk cache to the first (harmless startup errors: "already in use", "Unable to move the cache").
- **Autostart is a scheduled task per machine, `TagFoxAutostart`.** `scripts/autostart.ps1` starts the Everything *user* instance (the service runs as SYSTEM and does not host the HTTP server, so the user instance is the one TagFox needs) and then `npm start`, waiting for the HTTP port read from `%APPDATA%\Everything\Plugins-1.5a.ini`. It is idempotent, so its triggers can be generous: logon, session unlock and resume from sleep. Install or remove it with `pwsh scripts/install-autostart.ps1 [-Uninstall]`; no elevation needed. The task is not carried by git, so a fresh machine needs the installer run once, which `machine-parity.ps1 -Fix` does. It logs to `%LOCALAPPDATA%\TagFox\autostart.log`, and `scripts/start.js` adds a line there for every Electron exit (code, signal, minutes up), so a TagFox that vanished says whether it quit (code 0), was killed or crashed; there is no crash reporter, so no dump is ever written. An autostarted TagFox has no visible console, so kill it and run `npm start` by hand when you want the log live.
- **An edit to `main.js` never restarts TagFox; the header shows a Restart button instead (September 2026).** The reloader used to `app.relaunch()` on every main-process change, which starts the new process outside the terminal, so an agent editing `main.js` killed Steve's `npm start` window and left a TagFox he could not see the console of. `main.js` is now in the reloader's `ignore` list (renderer files still reload the window), main snapshots the mtime of every main-process module at startup, and `tagfox-runtime-info` reports what has changed since; the renderer polls it every 30s and on focus and shows `btnRestartTagFox`. `npm start` is `scripts/start.js`, which runs Electron and starts it again when it exits with code 75. Every restart goes through `restartTagFoxProcess()` in main: the Restart button (`tagfox-restart`), Ctrl+F5 and the View menu's restart. It exits with 75 under the wrapper, so TagFox stays in the same terminal, and falls back to `app.relaunch` outside it. Settings opens with a **Running now** block naming this TagFox (start time, PID, whether its code is current) and whichever gmist holds 5173, classified from the runner above the listener (`describeLocalGmistHolder`: `dev-local.mjs --built` is `preview:local`, `serve-gmist` is the bundled copy). Guarded by `test/restart-in-terminal.cjs`. `tags.js` is a main-process module as well, so an edit to it reloads the window and shows the Restart button, the same as `main.js`: the reloader counts only the modules main has required when the reloader is set up, which is `main.js` alone (measured October 2026).
  - **Main believes it is under the wrapper only when its parent process is the wrapper (`START_WRAPPER_EXIT_CODE`, October 2026).** The wrapper passes its code and its own PID in the environment, and main deletes both at startup. Environment variables outlive the wrapper: until this, a TagFox that Ctrl+F5 had relaunched outside the wrapper inherited `TAGFOX_START_WRAPPER`, so its next Restart exited with 75 and nothing was left to start it again. That is the likeliest account of TagFox vanishing on 23 October 2026, taking the global hotkey with it, minutes after a merge changed `main.js` and so showed the Restart button. The mechanism was reproduced in a throwaway instance, and guarded by the no-wrapper case in `test/restart-in-terminal.cjs`, which fails on the old code.
- **The dev reloader (`electron-reloader`, `npm start` only) polls the file tree only on a synced mount.** On local NTFS, `CHOKIDAR_USEPOLLING` cost 10% of a core in the main process forever and ~3,500 metadata ops/sec on the fs threadpool, which every other async fs call in main queued behind; native `fs.watch` costs nothing there and works. It survives a self-relaunch, because `app.relaunch()` inherits the environment, so measure after a cold `npm start`, never after the reloader has restarted itself. `_tmp` and `dist` are ignored, so writing scratch files no longer reloads Steve's window under him. Raise latency is logged to `%TEMP%\tagfox-mainperf.log` as `raise show=… to-paint=… away=…`.
- **The renderer must never be left at Chromium's background priority: `disable-renderer-backgrounding` (main.js, August 2026).** Chromium demotes a window's renderer to background mode whenever that window is hidden *or merely covered by another window*, which on Windows is `PROCESS_MODE_BACKGROUND_BEGIN`: Idle priority class, lowest I/O and memory priority, working set trimmed. Measured on STEVE-DELL: both TagFox renderers read `PriorityClass=Idle` for as long as the window was covered, while every other app on the machine stayed normal, and a Ctrl+Space raise then took 3-7s to first paint against ~50ms warm. That is the wrong policy for an app whose entire job is to appear instantly and take a keystroke, so the switch is set before `app.whenReady`, with `backgroundThrottling: false` on the window for the same reason (a hidden window's timers otherwise drop to 1Hz and then 1/min, so the first tick after a raise can be a second late). The cost is about 100MB kept resident while TagFox is off screen. Autostart is what made this bite: TagFox now sits covered for days instead of being started when wanted. **Assert it rather than trust the switch name** — with the window hidden or covered, `Get-Process` must show `PriorityClass=Normal` for the `--type=renderer` processes. The main process, which routes every click to the page, raises itself to Normal at startup for the same reason (September 2026): Windows passes a launcher's BelowNormal on to its children, the autostart task used Task Scheduler's default priority of 7 (BelowNormal), and an `app.relaunch` inherits whatever the old process had. The task now registers at 4, and `machine-parity.ps1` warns on one that does not.
- **Auto-refresh is on by default at 5 seconds, and a tick repaints only on a real change (September 2026).** The timer always re-ran the search, but every tick rebuilt the whole table whether or not the rows had moved, which dropped the scroll position, disposed and remade every tooltip and shifted the row under the pointer. So it sat at Off and the list went stale whenever files changed outside TagFox. A tick now sets `quietAutoRefreshRender`, and `renderTableImpl` compares `resultsTableRenderSignature()` (display paths in order, each with its modified time and size, so an edit in place counts) against the last one rendered and returns without touching the DOM when they match; a repaint that does happen restores `scrollTop`. `autoRefreshTickWouldDisturb()` skips the tick outright while the pointer is in the list, a drag is live, or **the list has been grown past its first page** — a refresh comes back with page one, so a tick after load-more would throw the extra pages away. That last test is `singleOffset > pageSize`, never `> 0`: `singleOffset` starts at the first page's own row count, and `> 0` silently stopped the timer for every non-empty search while the "nothing was rebuilt" assertion went on passing. A tick also writes nothing to the status line, since the early return skips the line that would put the hit count back, and a tick's "Searching…" used to stay there for good. None of this touches F5 or the header button, which always repaint and always report. The old Off is carried to 5s once, via `LS.autoRefreshDefaultMoved`. Guarded by `test/quiet-refresh.cjs`, whose positive control (a new file must still get through) is the half that matters, since a tick that never ran looks exactly like a tick that found nothing.
- **An explicit refresh must prove it ran: one choke point, `refreshResultsFromUi()` (renderer).** F5 arrives by two routes (main's `before-input-event` → `tagfox-plain-f5-refresh`, and the renderer's own keydown) and only while the page holds OS keyboard focus, which Steve loses often enough to report refreshes that never happened. So there is also a header button (`btnRefreshResults`, `fa-arrows-rotate`), since a click always lands, and all three routes go through the one function. It spins the button and reports `Refreshed hh:mm:ss — N row(s), unchanged` (or `+3 new, -1 gone`), because a refresh that finds nothing new is otherwise indistinguishable on screen from a keypress that never arrived, which is what "F5 sometimes does not refresh" turned out to describe. Do not reduce that status back to a bare row count. Guarded by `test/refresh-visible.cjs`.
- **`%TEMP%\tagfox-mainperf.log` is the one perf log, and both processes write to it.** Main logs `raise …` per raise (with per-process working set and CPU across the raise, so a slow one says whether it was paging or work), `eventloop-lag`, `ipc <channel>` over 500ms, `ipc-sync <channel>` over 100ms (a sync channel blocks the renderer for its whole duration), and `everything-search` over 800ms. The renderer sends its own jank through `window.tagBrowser.perfLog` (`longtask`, `lag`, `vis=`, `key … to-paint=`), rate-capped in main at 60 lines a minute. Thresholds are set so an ordinary session writes nothing, so any line in that file is a real stall. Read it before theorising about a slow TagFox. A test instance (`TAGFOX_TEST_HIDDEN`) writes to `tagfox-mainperf-test.log` instead, because test runs type and search far harder than Steve does and once made up most of the main log.
- **Recency means a file's own modified time, so a recency window excludes folders (`file:`) unless Folders only is on (October 2026).** The window was always `dm:>=…` in the Everything query, but Windows bumps a folder's modified time when a child is created, deleted or renamed and never when one is edited, so folder hits made the filter look as if it followed creation: measured on STEVE-DELL, 1,876 of the last hour's 10,186 hits were such folders. `appendRecencyToEverythingQuery` is the one place recency is applied; there is no client-side recency filter.
- After changing search, results rendering or paging in `renderer.js`, run `npm test`. The results/refresh concurrency is the most fragile part of the codebase; the historical bugs (searches rendering into a hidden pane; load-more rows lost on a background refresh; copy/delete bleeding between panes) are written up in the README concurrency section and guarded by the suite.
- **One results pane, and nothing renders anywhere else.** The search state is a `tabs` array (each entry: `searchState`, `lastRows`, `resultsPagingCtx`) whose active entry is the only one shown; any other entries are saved searches that nothing switches to. Nothing (search, F5, auto-refresh, CRUD) renders or mutates anything but the active entry. This single-pane model replaced the old A/B split in July 2026 and deleted its whole race/bleed bug class, so do not reintroduce background rendering of a second pane. `loadMoreResults()` copies the grown rows into the active entry in its `finally`, and every test's structural check compares them with the rows on screen.
- **Runner is the only layout on screen, and Classic's code is being deleted in stages (Steve, 24 October 2026).** Every real start applies Runner; Settings has no layout switch and `/` has no Classic command. A test instance still opens a fresh profile in Classic (`LS.toggleOpens` decides; the preload's `isTestInstance`, from `TAGFOX_TEST_HIDDEN`, says it is a test from the first page load, which the `#tagfoxtest` hash cannot, since the harness loads the page once without it), so the Classic tests go on guarding Classic code until that code is deleted, and a deletion stage takes its tests with it. Before deleting anything, read the task file "Delete the Classic layout's code in stages" at the repo root (what only Classic does, and the Classic code Runner still depends on, starting with the hidden controls that hold Runner's state). In Runner the header's Restart button sits in the search box (`placeRestartButtonForLayout`).
- **Runner is a layout of this renderer, never a fork (October 2026).** `body.tagfox-runner` hides Classic's chrome in CSS; anything Runner does differently is an `isRunnerMode()` branch inside the shared function (`runSearch`, `sortLastRowsForDisplay`, `renderTableImpl`, the key handler). A Runner-only copy of the search, the table, the Viewer or the favourites store is a defect. Stars are the favourites list, so favourites hold files as well as folders; `path-kinds` in main tells them apart, which is how Ctrl+Shift+1..9 (`openFavouritePath`) knows to open a file and go into a folder (`test/runner-stars.cjs`). Use counts are the existing `fileFocusStats`/`folderFocusStats`. Every ranking weight is in `RUNNER_RANK`. README "Runner layout" has the design; `test/runner-layout.cjs` guards it.
- **Taking anything off the Shelf recycles it, never deletes it (`clear-shelf` and `remove-shelf-paths` in `main.js` call `recycleListBatched`, October 2026).** A drop onto the Shelf moves the original into its staging folder, so a Shelf item is often the only copy of a file. Its × is one click with no question asked. Do not bring back a permanent delete there for speed or for files Node cannot remove. `test/runner-shelf.cjs` finds the item in the Recycle Bin.
- **Toggling TagFox in raises no overlay.** A keyboard overlay offering the open tabs plus saved searches and folders was removed in August 2026, because Steve found it more trouble than it was worth. Do not reintroduce an on-show overlay.
- **The toggle shortcut pressed from another app's Open or Save dialog sends the next pick to that dialog (prototype, 25 October 2026).** `toggleMainWindowFromGlobalShortcut` reads the foreground window before it raises TagFox (`file-dialog-handoff.js`: user32 through koffi, about 5µs a call, against a second a call for PowerShell and 13ms for a warm one). A standard file dialog (class `#32770`) with its file-name box becomes `fileDialogTarget`; the window handle stays in main, and the renderer is told the app, the title and the kind (`tagfox-file-dialog-target`), which shows `#fileDialogBar` above the box. While that is set, `keyboardActivateSelection` sends the row instead of opening it, so Enter, a double-click and Ctrl+1…9 all send. Ctrl+Enter sends the folder TagFox is showing and Esc stops; those three keys are `first: true` entries in `RUNNER_KEYS`, tried before the rest. Any hide of the window clears the target. When the window in front is not such a dialog, the toggle behaves exactly as before. **Four rules are load-bearing:**
  - Text goes only to the file-name box of the same dialog (same handle and process, found again at the moment of sending, and inside that dialog), by `WM_SETTEXT`, and is read back before anything is pressed.
  - The dialog's button is pressed (`WM_COMMAND` `IDOK`) only when it reads Open: a file then opens and a folder is navigated to.
  - A Save dialog, or one whose button says anything else, is only filled in, with the folder plus the name already in its box, and never pressed, because Save over an existing file brings up an overwrite prompt.
  - No keystrokes are synthesised, so nothing can land in whichever window has the focus.
  The file-name box is a visible `Edit` (control id 1148 in an Open dialog, 1001 in Save As) inside a `ComboBox`, and the address bar's `ToolbarWindow32` under `Breadcrumb Parent` reads "Address: <folder>" (measured on Windows 11). Guarded by `test/file-dialog-handoff.cjs` (the renderer half, hidden) and `test/manual-file-dialog.cjs`, which opens real Open and Save As dialogs on screen and so is run by hand only, after asking Steve (passed 25 October 2026). Not yet checked: a packaged build, where koffi's `.node` must come out of the asar (electron-builder unpacks `.node` files by default), and other apps' dialogs (Chrome's upload, Office).
- **The window's × hides TagFox and never quits it (25 October 2026).** Closing used to quit, which took the global shortcut with it, so Steve's next Ctrl+Alt+Space did nothing. The main window's `close` handler in `createWindow` turns a close into a hide unless `appQuitting` is set, which `before-quit` (File → **Quit TagFox**, labelled because the role reads "Exit" on Windows, and the `/` command **Quit TagFox** through `tagfox-quit`) and Windows' `query-session-end` set. `app.exit` (Restart) never raises the event. Guarded by `test/close-hides.cjs`, which posts the real `WM_CLOSE`: the renderer's `window.close()` skips the close event, so a test using it would pass on the old code.
- **Ctrl+Shift+Space is a third global shortcut: raise TagFox on the last hour's changes anywhere.** Fixed (`RECENT_TAB_ACCEL` in `main.js`), not in Settings like the toggle and Quick TODO. Main raises the window and sends `tagfox-open-recent-tab`, and the renderer's `openRecentTab()` resets the search in place: no query text, no scope folder, no tags, the last hour. Runner resets to its own defaults (`runnerResetAllFilters`); Classic turns every search option off except Match path (on by default, `optPath`) and shows subfolders, files and folders again. It is OS-wide, so there is no in-app key handler for it, and a failed registration (another app holds the combo) is only a startup `console.warn`. `test/runner-layout.cjs` and `test/recent-tab.cjs` cover the renderer half in each layout; the registration was checked once by sending a real keypress at a test instance.
- **Results column dividers: every `.th-resize` handle belongs to the th on the RIGHT of the boundary it drags** and straddles that th's left edge (`left:0; margin-left:-6px`). This is load-bearing, not styling. Each sticky header cell sits at `z-index: 4`, so equal-z siblings paint in DOM order and a handle hanging off a th's right edge is painted over by the next th: half the strip goes invisible and its clicks land on that th's sort instead, which is what made resizing feel unpredictable (fixed August 2026; one instance of the same bug had been patched for Actions|Size in July). The `data-resize-left`/`data-resize-right` pair still names colPercent indices 0–5 (chk, name, path, actions, size, modified), unchanged.
- **The Viewer's markdown write is armed by the editor, never by the preview, and refuses a file that has moved on disk (September 2026).** Selecting a `.md` or `.txt` file loads its text into the same buffer the editor uses. That buffer's write used to be armed by the load, and it flushes on blur, on the next selection and on a panel refresh, so TagFox saved a buffer nobody had typed into over whatever had written the file since. On a file Steve co-edits with an agent that reverted his work to the state it had when he last looked at it, seconds or hours later, with nothing on screen to say so; it cost him about 30% of his time for eight weeks and was blamed on five other things first. Three rules hold now: `flushMdFileAutosave` returns unless `mdFileEditorIsOpen()`, `openMdFileEditorFresh` re-reads the file before the editor opens so typing never starts from a stale buffer, and the write is refused with a status line when the bytes on disk differ from `mdAutosaveLoadedText`, which is what the buffer was loaded with. Do not arm the write anywhere else, and do not treat the refusal as an edge case: the writer it protects against is the common case here. Guarded by `test/md-preview-no-write.cjs`, whose positive control (an edit must still save) is the half that matters, since a fix that stopped saving altogether would pass the rest.
- **A splitter drag runs under a shield, and the Viewer pane is clamped to what the layout can give (August 2026).** The Viewer holds iframes and the PDF preview runs in its own process, so a drag that crossed one stopped delivering mouse moves to the page: the divider froze and then jumped when the pointer came back, which is what "the divider has a mind of its own" turned out to be. Every splitter drag now puts a fixed transparent `.tagfox-split-drag-shield` over the window (`addSplitDragShield`), which keeps every hit test in this document; the Viewer splitter also drags on pointer events with `setPointerCapture`, so a release outside the window ends the drag instead of leaving it live, and it starts on the left button only. Width is clamped by `maxPropsPaneWidthPx()` to what the results and Viewer panes share minus `RESULTS_PANE_MIN_PX`, read from those two elements rather than from a parent that also holds the splitter; the old fixed 1600px ceiling let CSS `max-width: 90vw` stop the panel while the drag counted on past it, so the pointer had to be dragged all the way back before anything moved, and the results pane could be squeezed to a sliver. `.split-v` is a 6px bar in a 22px grab band and hover only lights it up: it used to scale 2.3x, so the target moved as the pointer arrived and shrank again whenever a drag ran ahead of it. Guarded by `test/splitter-drag.cjs`.
- The tests drive the real app over CDP via a `#tagfoxtest` hook at the end of `renderer.js` (inert in normal runs). See memory `[[reference_electron_cdp_testing]]` for the general technique.
- **A PDF loads without the plugin's toolbar: fitted to the width in the side pane, at 150% when expanded.** The expanded Viewer (Shift+Space) is 90vw x 100vh. Chromium's PDF plugin reads its view parameters from the URL fragment, and only at load, so `setPdfFrameSrc`/`syncPdfViewParams` (renderer) remember the blob URL and rebuild the fragment (`PDF_VIEW_PARAMS_PANE`, `PDF_VIEW_PARAMS_THEATER`) whenever the Viewer enters or leaves the expanded state. **`toolbar=0` is the only thing that closes the plugin's thumbnail sidebar**, measured against the Electron PDF viewer at 1728px (September 2026): `pagemode=none` left the thumbnails where they were, while `toolbar=0` removed the sidebar and the toolbar together and still honoured `zoom=150`. The side pane is for a glance, so it drops the toolbar too and asks for `view=FitH` (Steve, 25 October 2026). Measured in a 438px pane, the plugin's zoom read 0.524 with that fragment and with none, which is an A4 page fitted to the pane; the fragment states the fit rather than relying on the default. The page counter, zoom buttons, print and download go with the toolbar; Ctrl+wheel still zooms and the header still carries Reload. **A hidden test window draws the plugin at the wrong size**, so a screenshot of a PDF taken through the harness says nothing about its zoom: read the plugin's own instead (`document.querySelector('pdf-viewer').viewport_.getZoom()` in its frame, over CDP). Do not spend another session on `pagemode`.
- **The Viewer's header is the only header (July 2026), and the Viewer is drawn in Runner's style (October 2026).** The header row is the type tile, the name and the actions for what is shown. Under it `#propsMetaLine` gives the tags, the size, the modified time and the folder the item is in (a click copies the full path). For a folder or a folder doc, `#propsNestedReadmeToggleWrap` holds the Folder doc | Thumbnails tabs, the Subfolders switch and New TODO. Mode blocks inside `#propsDetails` do not carry a title or button row of their own; per-mode actions live in the header, default `d-none`, toggled with their block (`btnPdfRefresh`, `btnMdFileRefresh`/`btnMdFileEdit` via `syncMdFileViewerButtons`). Loading, errors and the kinds TagFox cannot preview all go through `showPropsPlaceholder` (`withOpen` adds Open and Show in folder). The foot line (`syncPropsFootHint`) is read from whichever block is visible. Labelled actions are `.tagfox-viewer-pill`, icon-only ones `.tagfox-viewer-icon`, and in Runner the aside is a card on the canvas (`body.tagfox-runner #propsAside`). Guarded by `test/viewer-runner.cjs`.
- **The folder doc is two-state (`syncFolderDocHeaderExists`, `syncFolderDocChrome`).** Found on disk: a bar names the doc and offers Edit, which becomes Save beside Cancel while the editor is open. None yet: `#readmeEmptyState` says so and holds the name field (stem, extension, tags) beside Write it; while the new doc is being written, that field moves up into the bar, so there is one field in one of two slots. Do not show create or rename chrome while a found doc is displayed: starting a differently named second folder doc from there was dropped on purpose, since the Subfolders view reaches every doc. A folder doc writes only on Save; a text file saves as you type, so its Edit becomes Done and `#propsSaveState` reports what the last autosave did, from the write's own result.
- **New TODO is the Quick TODO box aimed at a folder (October 2026).** The folder view's New TODO and the `/` command "New TODO in this folder" call `showQuickTodoPop(folder)`; the global shortcut calls it with no folder, so the file goes in the Quick TODO folder from Settings. Every way of making a TODO uses that one box and one set of tags (`newTodoMdTags`).
- Dates in generated output / change stamps must not use year-less numeric form (global writing rule).
- **No `google-oauth-client.json` at the app root means every Drive-backed action reports a sign-in problem and opens nothing (19 August 2026).** The file is gitignored, so it does not travel with a clone, and STEVE-DELL had none: the cloud pen said "Open in gmist online: Google Drive sign-in is needed first (Settings)" and never built a URL, which reads as the online feature having broken. Mirrored Drive files carry no `:user.drive.id` stream either (checked with `Get-Item -Stream *`), so the API is the only route and there is no quiet fallback. README “Google Drive setup” names the copy to use; `machine-parity.ps1` now checks for the file under `oauth-client`. Two separate faults hid behind one symptom here: this one, and the browser TagFox handed the finished link to (see the sub-bullet under the child-window rule below). The second only became visible once the first was fixed.
- **Resolving a row's Google Drive file id: use `resolveGoogleDriveFileIdRobust` (main.js), not the thin `resolveGoogleDriveFileIdForPath`.** The robust one escalates: the local `:user.drive.id` stream, else hunt the parent folder id via a sibling that carries one (`inferGoogleDriveFolderIdFromChildItems`) and look the file up scoped to that folder (collision-safe for repeated names), else a unique exact-name Drive-API match. The thin resolver is stream-only and returns nothing for a mirrored file whose stream is unreadable. The stream path needs no API; the fallbacks need Google sign-in (the `google-oauth-client.json` OAuth account, same as "Open in Google Workspace" / "Create Google Doc here").
  - **The `:user.drive.id` read is synchronous and escalates to cmd and then PowerShell, so it must never run per file over a folder.** Measured on STEVE-DELL, 19 August 2026: one escalation costs about 700ms, and the parent-folder inference ran it for every sibling, which froze the main process for 19 seconds on a single click (`eventloop-lag 19133ms` next to `ipc resolve-google-drive-file-id 21516ms` in the perf log) and made the cloud pen take 20s to open a tab. Mirror-mode Drive carries no such stream on any file, so every one of those spawns was always going to fail. The scan now reads every sibling with the plain Node read only (`{ cheapOnly: true }`, 4ms for the whole folder) and pays the escalation on at most `ADS_ESCALATION_BUDGET` of them, then remembers a streamless folder for ten minutes so the next click skips even that. Keep the cheap pass over the whole folder: the bound belongs on how hard each file is tried, not on how many files are looked at.

## Open in gmist / Google Workspace (the row edit-pen icon)

The results-row edit icon (pen, `btnGmist` in `renderer.js`) opens the row for online editing. It routes by file type, all gated on the file being under a Google Drive mount (`pathUnderGoogleDrive`):

- `.md`/`.qmd` → **gmist**, with a button PER applicable mode so Steve picks local vs online per click (chosen July 2026 over an automatic local-first default; he sometimes wants the deployed version). A markdown row shows:
  - a **local** pen (`fa-pen-to-square`) on every markdown row of a machine that has a gmist (see the machine features bullet below), opening `http://localhost:5173/open?path=<absolute path>` **in a TagFox child window** (see the web editor window below): any file on any drive (C:, G:, H:), no Drive lookup, no sign-in, no name ambiguity, and it works for files not in Drive at all;
  - an **online** cloud (`fa-cloud`) when the file is under a Drive mount, opening the deployed worker `https://mist.broad-smoke-cc64.workers.dev/open?file=<id>&p=<readable home-relative path>` (needs the file's Drive id, resolved from the local mirror).
  So a Drive markdown file shows both, and a file outside Drive shows only the local pen. They are separate actions (`openRowInLocalGmist` / `openRowInOnlineGmist`), not a fallback chain. gmist mints the room and owns both `/open` contracts (see gmist's `CLAUDE.md`, local mode and the `GET /open` route); `&p=` is a harmless legibility breadcrumb gmist ignores. Auth is the browser's gmist session (bypassed in local mode), so TagFox holds no gmist credentials, and it never touches the localfs sidecar or its token.

## Print markdown to PDF (the row PDF icon)

Markdown rows carry a `fa-file-pdf` button beside the two gmist pens, and the row `⋯` actions menu carries the same thing as a **Print to PDF** submenu. Both write a sibling `<name>.pdf`.

- **The renderer is JobCat's `make_pdf.py`, run as a subprocess, so TagFox holds no PDF styling of its own.** JobCat's `CLAUDE.md` section 4 is canonical for the flags and the profiles, so change the house PDF there. `main.js` runs the script with `cwd` set to the JobCat folder, because it resolves its logo (`img/…`) against the working folder, and passes absolute `--input`/`--output` through argv with no shell, so the spaces in a Drive path survive.
- **Three profiles, chosen per click: plain (`--type none`), Causal Map branded, Steve Powell branded.** A personal note and a client proposal want different branding, so the click opens a small native menu rather than assuming one, the same per-click choice the local and online gmist pens offer.
- **The JobCat folder and the Python interpreter are both resolved at run time.** JobCat: `jobcatDir` in `tagfox-make-pdf.json` (userData), else the Drive copy built from the home folder, else a sibling checkout or `C:\dev\JobCat`; each candidate must actually carry `make_pdf.py`. - **An existing PDF of that name is never replaced without asking**, since a downloaded `report.pdf` often sits beside `report.md`. Main returns `{exists:true}` and the renderer confirms before a second call with `overwrite`.
- **A run reports a PDF only when the output is on disk and non-empty**, because `make_pdf.py` can print a traceback and still exit 0. - **`make_pdf.py` does not embed body images**, so a markdown file whose pictures matter still wants Quarto or the garden PDF route.
