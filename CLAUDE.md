# TagFox

Electron desktop UI over the local [Voidtools Everything](https://www.voidtools.com/) HTTP server. No backend; it talks only to Everything and the local filesystem. Main editor: Cursor.

Role: the tool Steve reaches for a hundred times a day, so it has to work in his hands rather than in a test. Measure what is on screen before designing for it; land the work on `main` in `C:\dev\TagFox`, where he runs it; prove it in the running app before calling it done. Ledger: `_role.md`.

## Working rules

- **A background job here runs directly in `C:\dev\TagFox`, not an isolated worktree** (`.claude/settings.json` sets `worktree.bgIsolation: none`). A fresh worktree carries no `node_modules`, so a job confined to one could edit but never run `npm test` or `npm run dist`, and the result has to land in this checkout anyway since it's where Steve runs the app. See memory `[[background-jobs-and-worktrees]]` for the general rule and the escape hatch.
- **Steve runs TagFox with `npm start`, always. He never installs the packaged app.** So `npm run dist` exists only to hand Gabriele a build (the installer is copied to the Causal Map Drive root by `scripts/run-dist.js`); build it when asked to ship, and never install or update an exe on Steve's machine. When diagnosing his running app, it is the working tree, not a packaged build. A second running instance is another `npm start`, which loses the global hotkeys and the Chromium disk cache to the first (harmless startup errors: "already in use", "Unable to move the cache").
- **Autostart is a scheduled task per machine, `TagFoxAutostart`.** `scripts/autostart.ps1` starts the Everything *user* instance (the service runs as SYSTEM and does not host the HTTP server, so the user instance is the one TagFox needs) and then `npm start`, waiting for the HTTP port read from `%APPDATA%\Everything\Plugins-1.5a.ini`. It is idempotent, so its triggers can be generous: logon, session unlock and resume from sleep. Install or remove it with `pwsh scripts/install-autostart.ps1 [-Uninstall]`; no elevation needed. The task is not carried by git, so a fresh machine needs the installer run once, which `machine-parity.ps1 -Fix` does. It logs to `%LOCALAPPDATA%\TagFox\autostart.log`; an autostarted TagFox has no visible console, so kill it and run `npm start` by hand when you want the log live.
- **The dev reloader (`electron-reloader`, `npm start` only) polls the file tree only on a synced mount.** On local NTFS, `CHOKIDAR_USEPOLLING` cost 10% of a core in the main process forever and ~3,500 metadata ops/sec on the fs threadpool, which every other async fs call in main queued behind; native `fs.watch` costs nothing there and works. It survives a self-relaunch, because `app.relaunch()` inherits the environment, so measure after a cold `npm start`, never after the reloader has restarted itself. `_tmp` and `dist` are ignored, so writing scratch files no longer reloads Steve's window under him. Raise latency is logged to `%TEMP%\tagfox-mainperf.log` as `raise show=… to-paint=… away=…`.
- **The renderer must never be left at Chromium's background priority: `disable-renderer-backgrounding` (main.js, August 2026).** Chromium demotes a window's renderer to background mode whenever that window is hidden *or merely covered by another window*, which on Windows is `PROCESS_MODE_BACKGROUND_BEGIN`: Idle priority class, lowest I/O and memory priority, working set trimmed. Measured on STEVE-DELL: both TagFox renderers read `PriorityClass=Idle` for as long as the window was covered, while every other app on the machine stayed normal, and a Ctrl+Space raise then took 3-7s to first paint against ~50ms warm. That is the wrong policy for an app whose entire job is to appear instantly and take a keystroke, so the switch is set before `app.whenReady`, with `backgroundThrottling: false` on the window for the same reason (a hidden window's timers otherwise drop to 1Hz and then 1/min, so the first tick after a raise can be a second late). The cost is about 100MB kept resident while TagFox is off screen. Autostart is what made this bite: TagFox now sits covered for days instead of being started when wanted. **Assert it rather than trust the switch name** — with the window hidden or covered, `Get-Process` must show `PriorityClass=Normal` for the `--type=renderer` processes.
- **Auto-refresh is on by default at 5 seconds, and a tick repaints only on a real change (September 2026).** The timer always re-ran the search, but every tick rebuilt the whole table whether or not the rows had moved, which dropped the scroll position, disposed and remade every tooltip and shifted the row under the pointer. So it sat at Off and the list went stale whenever files changed outside TagFox. A tick now sets `quietAutoRefreshRender`, and `renderTableImpl` compares `resultsTableRenderSignature()` (display paths in order, each with its modified time and size, so an edit in place counts) against the last one rendered and returns without touching the DOM when they match; a repaint that does happen restores `scrollTop`. `autoRefreshTickWouldDisturb()` skips the tick outright while the pointer is in the list, a drag is live, or **the list has been grown past its first page** — a refresh comes back with page one, so a tick after load-more would throw the extra pages away. That last test is `singleOffset > pageSize`, never `> 0`: `singleOffset` starts at the first page's own row count, and `> 0` silently stopped the timer for every non-empty search while the "nothing was rebuilt" assertion went on passing. None of this touches F5 or the header button, which always repaint and always report. The old Off is carried to 5s once, via `LS.autoRefreshDefaultMoved`. Guarded by `test/quiet-refresh.cjs`, whose positive control (a new file must still get through) is the half that matters, since a tick that never ran looks exactly like a tick that found nothing.
- **An explicit refresh must prove it ran: one choke point, `refreshResultsFromUi()` (renderer).** F5 arrives by two routes (main's `before-input-event` → `tagfox-plain-f5-refresh`, and the renderer's own keydown) and only while the page holds OS keyboard focus, which Steve loses often enough to report refreshes that never happened. So there is also a header button (`btnRefreshResults`, `fa-arrows-rotate`), since a click always lands, and all three routes go through the one function. It spins the button and reports `Refreshed hh:mm:ss — N row(s), unchanged` (or `+3 new, -1 gone`), because a refresh that finds nothing new is otherwise indistinguishable on screen from a keypress that never arrived, which is what "F5 sometimes does not refresh" turned out to describe. Do not reduce that status back to a bare row count. Guarded by `test/refresh-visible.cjs`.
- **`%TEMP%\tagfox-mainperf.log` is the one perf log, and both processes write to it.** Main logs `raise …` per raise (with per-process working set and CPU across the raise, so a slow one says whether it was paging or work), `eventloop-lag`, `ipc <channel>` over 500ms, `ipc-sync <channel>` over 100ms (a sync channel blocks the renderer for its whole duration), and `everything-search` over 800ms. The renderer sends its own jank through `window.tagBrowser.perfLog` (`longtask`, `lag`, `vis=`, `key … to-paint=`), rate-capped in main at 60 lines a minute. Thresholds are set so an ordinary session writes nothing, so any line in that file is a real stall. Read it before theorising about a slow TagFox.
- After changing search, results rendering, paging, or the result-tabs logic in `renderer.js`, run `npm test`. The results/refresh concurrency is the most fragile part of the codebase; the historical bugs (searches rendering into a hidden pane; load-more rows lost on a background refresh; copy/delete bleeding between panes) are written up in the README concurrency section and guarded by the suite.
- **Only the active tab has DOM; inactive tabs are pure state.** The results area is one visible pane driven by a `tabs` array (each entry: `searchState`, `lastRows`, `resultsPagingCtx`). Switching tabs saves the live UI into the leaving tab and loads the entering one; the active tab re-runs its search on activation. Nothing (search, F5, auto-refresh, CRUD) renders or mutates any tab but the active one. This single-visible-pane model is what replaced the old A/B split in July 2026 and deleted its whole race/bleed bug class, so do not reintroduce background rendering of a second pane. `loadMoreResults()` must persist the grown rows into the active tab in its `finally` or a later tab switch reverts to the pre-load-more page.
- **The global-hotkey tab switcher is retired (removed August 2026).** Toggling TagFox in used to raise a keyboard overlay offering the open tabs plus saved searches and folders. Steve found it more trouble than it was worth, so the whole feature is gone: the overlay, its `tagfox-open-tab-switcher` IPC, the `optSwitcherOnToggle` setting, and `openNewTab`'s `evictOldest` option, which nothing else used. Switching tabs is manual again (the tab strip, or `cycleTab`). Do not reintroduce an on-show overlay.
- **Results column dividers: every `.th-resize` handle belongs to the th on the RIGHT of the boundary it drags** and straddles that th's left edge (`left:0; margin-left:-6px`). This is load-bearing, not styling. Each sticky header cell sits at `z-index: 4`, so equal-z siblings paint in DOM order and a handle hanging off a th's right edge is painted over by the next th: half the strip goes invisible and its clicks land on that th's sort instead, which is what made resizing feel unpredictable (fixed August 2026; one instance of the same bug had been patched for Actions|Size in July). The `data-resize-left`/`data-resize-right` pair still names colPercent indices 0–5 (chk, name, path, actions, size, modified), unchanged. Pair 2|3 lives on the Actions th and serves both views, since tree view hides Path and folds its weight into Name, leaving the same visible boundary.
- **A splitter drag runs under a shield, and the Viewer pane is clamped to what the layout can give (August 2026).** The Viewer holds iframes and the PDF preview runs in its own process, so a drag that crossed one stopped delivering mouse moves to the page: the divider froze and then jumped when the pointer came back, which is what "the divider has a mind of its own" turned out to be. Every splitter drag now puts a fixed transparent `.tagfox-split-drag-shield` over the window (`addSplitDragShield`), which keeps every hit test in this document; the Viewer splitter also drags on pointer events with `setPointerCapture`, so a release outside the window ends the drag instead of leaving it live, and it starts on the left button only. Width is clamped by `maxPropsPaneWidthPx()` to what the results and Viewer panes share minus `RESULTS_PANE_MIN_PX`, read from those two elements rather than from a parent that also holds the favourites column; the old fixed 1600px ceiling let CSS `max-width: 90vw` stop the panel while the drag counted on past it, so the pointer had to be dragged all the way back before anything moved, and the results pane could be squeezed to a sliver. `.split-v` is a 6px bar in a 22px grab band and hover only lights it up: it used to scale 2.3x, so the target moved as the pointer arrived and shrank again whenever a drag ran ahead of it. Guarded by `test/splitter-drag.cjs`.
- The tests drive the real app over CDP via a `#tagfoxtest` hook at the end of `renderer.js` (inert in normal runs). See memory `[[reference_electron_cdp_testing]]` for the general technique.
- **The expanded Viewer is 90vw x 100vh, and its PDF opens at 150% with no sidebar (September 2026).** Shift+Space fills the screen, which is wide enough that Chromium's PDF plugin opens its thumbnail sidebar on its own and 100% leaves the text small. The plugin reads its view parameters from the URL fragment and only at load, so `setPdfFrameSrc`/`syncPdfViewParams` (renderer) remember the blob URL and rebuild the fragment whenever the Viewer enters or leaves the expanded state. **`toolbar=0` is the only thing that closes that sidebar**, measured against the Electron PDF viewer at 1728px: `pagemode=none` left the thumbnails exactly where they were, and `toolbar=0` removed the sidebar and the plugin's toolbar together while still honouring `zoom=150`. So the page counter, zoom buttons, print and download go with the sidebar; Ctrl+wheel still zooms and the panel header still carries Refresh. The side pane is narrow enough to show no sidebar, so it keeps the plugin's own defaults and loads with no fragment at all. Do not spend another session on `pagemode`.
- **The viewer panel header is the only header (July 2026).** Mode blocks inside `#propsDetails` (text file, PDF, image, office…) must not carry their own title/button rows; per-mode actions live in the panel header, default `d-none`, toggled with their block (pattern: `btnPdfRefresh`, `btnMdFileRefresh`/`btnMdFileEdit` via `syncMdFileViewerButtons`). The folder-mode "Folder doc" row is two-state (`syncFolderDocHeaderExists`): doc found on disk → read-only name label; no doc yet → editable stem + tags, where Edit + Save creates the file. Do not show create/rename chrome while a found doc is displayed — deliberately dropped: starting a differently named second folder doc from that row (nested view reaches every doc instead).
- Dates in generated output / change stamps must not use year-less numeric form (global writing rule).
- **No `google-oauth-client.json` at the app root means every Drive-backed action reports a sign-in problem and opens nothing (19 August 2026).** The file is gitignored, so it does not travel with a clone, and STEVE-DELL had none: the cloud pen said "Open in gmist online: Google Drive sign-in is needed first (Settings)" and never built a URL, which reads as the online feature having broken. Mirrored Drive files carry no `:user.drive.id` stream either (checked with `Get-Item -Stream *`), so the API is the only route and there is no quiet fallback. README “Google Drive setup” names the copy to use; `machine-parity.ps1` now checks for the file under `oauth-client`. Two separate faults hid behind one symptom here: this one, and the browser TagFox handed the finished link to (see the sub-bullet under the child-window rule below). The second only became visible once the first was fixed.
- **Resolving a row's Google Drive file id: use `resolveGoogleDriveFileIdRobust` (main.js), not the thin `resolveGoogleDriveFileIdForPath`.** The robust one escalates: the local `:user.drive.id` stream, else hunt the parent folder id via a sibling that carries one (`inferGoogleDriveFolderIdFromChildItems`) and look the file up scoped to that folder (collision-safe for repeated names), else a unique exact-name Drive-API match. The thin resolver is stream-only and returns nothing for a mirrored file whose stream is unreadable. The stream path needs no API; the fallbacks need Google sign-in (the `google-oauth-client.json` OAuth account, same as "Open in Google Workspace" / "Create Google Doc here").
  - **The `:user.drive.id` read is synchronous and escalates to cmd and then PowerShell, so it must never run per file over a folder.** Measured on STEVE-DELL, 19 August 2026: one escalation costs about 700ms, and the parent-folder inference ran it for every sibling, which froze the main process for 19 seconds on a single click (`eventloop-lag 19133ms` next to `ipc resolve-google-drive-file-id 21516ms` in the perf log) and made the cloud pen take 20s to open a tab. Mirror-mode Drive carries no such stream on any file, so every one of those spawns was always going to fail. The scan now reads every sibling with the plain Node read only (`{ cheapOnly: true }`, 4ms for the whole folder) and pays the escalation on at most `ADS_ESCALATION_BUDGET` of them, then remembers a streamless folder for ten minutes so the next click skips even that. Keep the cheap pass over the whole folder: the bound belongs on how hard each file is tried, not on how many files are looked at.

## Open in gmist / Google Workspace (the row edit-pen icon)

The results-row edit icon (pen, `btnGmist` in `renderer.js`) opens the row for online editing. It routes by file type, all gated on the file being under a Google Drive mount (`pathUnderGoogleDrive`):

- `.md`/`.qmd` → **gmist**, with a button PER applicable mode so Steve picks local vs online per click (chosen July 2026 over an automatic local-first default; he sometimes wants the deployed version). A markdown row shows:
  - a **local** pen (`fa-pen-to-square`) on every markdown row, opening `http://localhost:5173/open?path=<absolute path>` **in a TagFox child window** (see the web editor window below): any file on any drive (C:, G:, H:), no Drive lookup, no sign-in, no name ambiguity, and it works for files not in Drive at all;
  - an **online** cloud (`fa-cloud`) when the file is under a Drive mount, opening the deployed worker `https://mist.broad-smoke-cc64.workers.dev/open?file=<id>&p=<readable home-relative path>` (needs the file's Drive id, resolved from the local mirror).
  So a Drive markdown file shows both, and a file outside Drive shows only the local pen. They are separate actions (`openRowInLocalGmist` / `openRowInOnlineGmist`), not a fallback chain. gmist mints the room and owns both `/open` contracts (see gmist's `CLAUDE.md`, local mode and the `GET /open` route); `&p=` is a harmless legibility breadcrumb gmist ignores. Auth is the browser's gmist session (bypassed in local mode), so TagFox holds no gmist credentials, and it never touches the localfs sidecar or its token.
- **"Copy gmist share link" on the row context menu, for handing a file to a collaborator (28 August 2026).** A markdown row's `⋯` menu carries a submenu offering a suggest link or an edit link. Both open the file in the deployed gmist with `&share=<role>` appended. gmist then puts the resulting link on the clipboard once the room is up (its `ShareOnOpen`). The copying has to happen over there because the gmist session cookie lives in the browser, so TagFox cannot mint a room or read back its URL. Suggest is listed first, since a reviewer who cannot rewrite the file underneath you is the usual case. The menu entry is gated on the file being markdown and nothing more: whether it is actually in Drive is `openRowInOnlineGmist`'s call, which owns `pathUnderGoogleDrive` and the id resolver and already words that failure properly. Do not add a second Drive-path test in `main.js` to hide the entry, or the rule lives in two processes.
- **Markdown opens in a local gmist by default (August 2026), not in the shell.** `.md`/`.qmd` route to `openRowInLocalGmist` from the one choke point every open path goes through (`openFileDefaultOrGoogleWorkspace`), so the row Open button, Enter and a double-click all land in gmist, starting it first if it is down. The way back to Obsidian or whatever holds the association is the row context menu, whose existing "Open" entry is relabelled **"Open with default app"** for markdown (`isMarkdownFilePath` in `main.js`); that entry runs in main and never touches the renderer's routing. The Viewer's own inline markdown editor is unaffected.
- **The installer carries a runnable gmist, so a machine with no checkout still opens markdown locally (24 August 2026).** Markdown routes to local gmist by default, and `findLocalGmistRepoDir()` only ever found a `mist` checkout, so the build handed to Gabriele answered "could not find the gmist repo" for every markdown row: the default open, Enter and double-click all dead, with the context menu the only way in. `scripts/bundle-gmist.js` now stages `_gmist/` at `predist` and electron-builder ships it as `resources/gmist`; `serve-gmist.cjs` runs it. A checkout still wins where there is one (`startLocalGmist` tries `findLocalGmistRepoDir` first), so Steve keeps `npm run dev:local` and hot reload, and the bundle is what every other machine runs. `TAGFOX_GMIST_FORCE_BUNDLED=1` exercises the bundled path here, since otherwise the packaged behaviour can never run on the machine it is written on, which is the shape of the bug itself. Stop the dev gmist first: both want 5173 and 5199.
  - **Miniflare, not `wrangler dev`, and no second node runtime.** gmist is a Worker with a Durable Object, so it needs workerd whichever route is taken, but Miniflare is the embedding API while wrangler is a developer CLI. Measured 24 August 2026: under `ELECTRON_RUN_AS_NODE` wrangler's arg parsing breaks, because yargs' `hideBin()` drops one fewer argv entry when it sees `process.versions.electron` without `process.defaultApp`, so wrangler reads its own script path as a command; past that (a shim setting `defaultApp`) its dev server started workerd and then never bound its port. Miniflare starts clean under Electron's own binary as node, which is also why the installer carries no `node.exe`. Payload is 116MB staged and about 26MB on the installer (84MB to 110MB), because workerd's 81MB binary compresses well.
  - **Two things in `serve-gmist.cjs` are load-bearing.** `assets: { routerConfig: { has_user_worker: true } }` or the asset router answers 404 for every route the worker owns, so `/go` and `/open` never reach gmist at all. And every module the build emitted has to be listed by name, with `index.js` first, because Miniflare cannot follow the dynamic imports between the built chunks and says so with `ERR_MODULE_DYNAMIC_SPEC`.
  - **The sidecar token and session secret are generated per install into `tagfox-local-gmist.json` (userData), never shipped.** The token is the sidecar's whole access control over a server that reads and writes any file the user can, so one baked into the installer would be the same secret on every machine. `bundle-gmist.js` also drops `.dev.vars` from the staged build, which react-router copies into `build/server`: it holds Steve's own session secret and sidecar token. Assert that: `find resources/gmist -name ".dev.vars"` must come back empty on a built installer.
  - **Gabriele's gmist is pinned to her TagFox.** The bundle is built from the `mist` checkout at package time, so a gmist change reaches her only in the next TagFox installer. Rebuild and re-copy when a gmist fix matters to her.
- **The local pen starts gmist when it is not running (`start-local-gmist`), rather than hiding itself.** Until August 2026 the button appeared only while a probe said gmist was up, so a stopped dev server silently removed it, which reads as the feature having been deleted; that is exactly how it got reported. The click now probes (`probe-local-gmist` → `HEAD /go`, 600ms, cached 5s), and on a miss runs `npm run dev:local` and waits for `/go` to answer (up to 150s; a cold sidecar-plus-vite start measured about a minute). Three things about the spawn are load-bearing, all measured 11 August 2026:
  - **`shell: true` and NOT `detached`.** `detached: true` on Windows gives the child a new console, so the grandchildren that matter (npm → node → vite) write there instead of the inherited log handle, and the parent stops receiving `exit` at all: a failed start then looks exactly like a slow one. Non-detached still outlives TagFox, since Windows does not kill children when a parent exits; it dies only with the console TagFox was launched from.
  - **Output goes to `%LOCALAPPDATA%\TagFox\gmist-local.log`**, and a failure reports the tail of it. The common failure is a stale localfs sidecar still holding 5199, which `dev:local` explains in its own words and then exits 1; without the log that arrives as a bare timeout.
  - **The repo is found, not hardcoded:** a `repoDir` in `tagfox-local-gmist.json` (userData), else a sibling `mist` checkout, else `C:\dev\mist`, and each candidate must actually carry a `dev:local` script.
  - **Whether the ports are held settles "is gmist up", and no HTTP probe is allowed near that question (31 August 2026).** A probe that says "down" about a gmist that is up is the worst case. The start that follows dies on the sidecar port the running gmist already holds, so `dev:local exited straight away (code 1)` arrives on screen and reads as a broken feature. Steve hit that on 18 August and again on 31 August, both times on a gmist whose dev server and sidecar had been up for hours. The reason no timeout can be tuned to fix it: measured against a gmist up for three days, `HEAD /go` answered in 1.3s, 1.6s, 1.9s, 3.3s and 3.3s on one run, then 2.6s, 4.9s, 6.1s, 9.0s and 11.3s twenty minutes later, because the dev server re-evaluates the worker entry per request. The old budget was 600ms, so it called a healthy gmist down on nearly every click. A probe is a slow judgement about a slow server and can never be the guard. `portIsHeld()` is: it asks the OS to bind the port, which answers in microseconds and needs no subprocess. So `startLocalGmist` reads 5173 and 5199 first. **5173 held means gmist is there**, so return at once and let the window wait out however long the page takes. **5199 held with 5173 free** is the orphaned sidecar `dev:local` refuses on, reported with its PID rather than after a doomed spawn and a log tail. **Both free** means nothing is listening, so spawn without probing at all: an "up after all?" check there would time out on every cold start for an answer already known. Guarded by `test/gmist-start-guard.cjs`, which holds each port with a socket that accepts and never answers, the worst case for a probe and the easy case for this.
  - **Use `portIsHeld()` on any path a click waits for, and `listenersByPort()` only to name a culprit.** `netstat -ano` measured 2.2s on this machine, against 116ms for the whole IPC round trip once the bind check replaced it, so netstat belongs on error paths alone. Both look at `127.0.0.1` and `[::1]`, because the vite dev server binds `[::1]` only: a bind test against `127.0.0.1` alone would succeed and call the port free, and `netstat -p tcp` would list IPv4 only and miss the dev server entirely. `probeLocalGmistOnce` keeps the same pair for the same reason. Its one remaining job is the wait during a cold start, on a single generous budget (`LOCAL_GMIST_PROBE_PATIENT_MS`), where a server coming up has to be given time to answer.
  - **A failed start names what is holding the ports.** `localGmistPortHolderHint()` reads the listeners on 5173 and 5199 and appends `PID … / taskkill /PID … /F`, because gmist's own message says to stop the sidecar without saying which process that is. It shells `netstat -ano`, never `-p tcp`, which lists IPv4 only and would miss the `[::1]` dev server.
- **One child-window mechanism serves both editors (`openWebEditorWindow`, August 2026).** The framed window Google Docs use (a BrowserWindow holding a toolbar BrowserView over a content BrowserView, with remembered bounds) now takes a kind from `WEB_EDITOR_KINDS` in `main.js`, which carries everything site-specific: the URL allowlist for loads and for the address bar, the session partition, the bounds file, and whether the Google-only "Expand" button shows. `googleWorkspace` is the old behaviour unchanged; `gmistLocal` allows only the `localhost:5173` origin. The toolbar is `web-editor-toolbar.html` plus its preload (renamed from `google-workspace-toolbar.*`), and its IPC channels are `webedit-toolbar-*`.
- **A minimised doc window is a desktop stub, not a taskbar button, and only its ICON can carry a name (23 August 2026).** A gmist or Workspace window is owned by the main window (`parent:`), so the shell gives it no taskbar button: minimising it leaves the legacy 160x28 caption stub at the bottom of the desktop. Measured on STEVE-DELL with four doc windows open: stubs sit in 160px slots along `y = workArea bottom`, and the themed stub draws **no caption text at all**, whatever `setTitle` says. (A `PrintWindow` capture is misleading here, because it renders the classic theme, which does draw about four characters. Capture the live screen instead.) So a window title alone leaves a row of identical Electron atoms, which is what Steve reported. `webEditorIconAbbrev` takes TWO characters from the filename and `applyWebEditorWindowIcon` has the window's own toolbar page rasterise them to a 16 and 32px PNG on a canvas, which becomes the window icon: the row then reads RE, AL, NO. Two is not a compromise to revisit, it is the measured ceiling. Three across, six stacked as two rows of three, and eight as two rows of four were each opened, minimised and captured at real size on 23 August 2026; Steve called the six-letter version invisible on his screen and it is. The square is 16px, so every extra character comes straight off the glyph size. Because two characters collide easily, the pair is chosen against the windows already open: the first two letters normally, else the first letter with the second word's initial, then with each later letter, then with a digit. README.md, readme notes.md and reference sheet.md open as RE, RN and RS. The ground colour is hashed from the pair as well (`webEditorIconHue`, ten hues at least 30 degrees apart), so a document keeps its colour between sessions and a row of pills separates by colour before anyone reads the letters. It steps to the next free hue on a clash, for the same reason the letters do. A raw hue from the hash was tried first and rejected: six test names gave three near-identical greens, because neighbouring hues in the yellows read as one colour at 16px. The canvas is in `web-editor-toolbar.html` because a BrowserView is the only text rasteriser here. The full name still goes on the window title and into the toolbar strip, for the restored window and for alt-tab.
- **Only LOCAL gmist opens in a TagFox window; online gmist still goes to the default browser.** A child window is its own cookie jar, and local mode needs no sign-in, so embedding it costs nothing. The deployed worker signs in with Google OAuth, which Google may refuse inside an Electron view, and Steve's gmist session already lives in his browser. Do not move the cloud pen into a window without testing that sign-in.
  - **Ask the shell which browser, never work it out from the registry (19 August 2026).** `openUrlInSystemDefaultBrowser` used to read `UrlAssociations\https\UserChoice` and spawn that ProgId's command. On STEVE-DELL that key says `MSEdgeHTM` while Windows itself opens Chrome, so every gmist link TagFox opened landed in Edge, which holds no gmist session, and the page answered `{"error":"sign in required"}` while Steve rightly insisted Chrome was his default. Measured: `start https://…` launched Chrome, the key said Edge, and the ProgId command behind it is `msedge.exe`. ## Print markdown to PDF (the row PDF icon)

Markdown rows carry a `fa-file-pdf` button beside the two gmist pens, and the row `⋯` actions menu carries the same thing as a **Print to PDF** submenu. Both write a sibling `<name>.pdf`.

- **The renderer is JobCat's `make_pdf.py`, run as a subprocess, so TagFox holds no PDF styling of its own.** JobCat's `CLAUDE.md` section 4 is canonical for the flags and the profiles, so change the house PDF there. `main.js` runs the script with `cwd` set to the JobCat folder, because it resolves its logo (`img/…`) against the working folder, and passes absolute `--input`/`--output` through argv with no shell, so the spaces in a Drive path survive.
- **Three profiles, chosen per click: plain (`--type none`), Causal Map branded, Steve Powell branded.** A personal note and a client proposal want different branding, so the click opens a small native menu rather than assuming one, the same per-click choice the local and online gmist pens offer.
- **The JobCat folder and the Python interpreter are both resolved at run time.** JobCat: `jobcatDir` in `tagfox-make-pdf.json` (userData), else the Drive copy built from the home folder, else a sibling checkout or `C:\dev\JobCat`; each candidate must actually carry `make_pdf.py`. Python: a real `%LOCALAPPDATA%\Programs\Python\Python3*\python.exe` ahead of a bare `python`, which on Windows is often the WindowsApps stub that opens the Store and runs nothing.
- **An existing PDF of that name is never replaced without asking**, since a downloaded `report.pdf` often sits beside `report.md`. Main returns `{exists:true}` and the renderer confirms before a second call with `overwrite`.
- **A run reports a PDF only when the output is on disk and non-empty**, because `make_pdf.py` can print a traceback and still exit 0. Its output goes to `%LOCALAPPDATA%\TagFox\make-pdf.log` and a failure carries the tail of that log. A run takes about 7 seconds (Chromium launch), so the status line says it started and then names what it wrote.
- **`make_pdf.py` does not embed body images**, so a markdown file whose pictures matter still wants Quarto or the garden PDF route.
