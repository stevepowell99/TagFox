# Test harness startup sometimes hangs before the test hook appears

A test TagFox occasionally never exposes `#tagfoxtest`: the harness waits its full 45 seconds and fails with "#tagfoxtest hook never appeared", with the renderer hung. It hits a different test each time and the test passes when rerun alone.

- **Cause found and fixed (25 October 2026): the hash was set on the blank page before `index.html`.** `findPageTarget` returns as soon as the target is listed under `index.html`, while the window can still be on the blank page that load replaces; the hash and reload were then dropped and `index.html` loaded without the hook, which is why every hang showed `readyState: complete` and an href without the hash. A re-arming harness counted it at two starts in three under another suite's load. `connect()` now sets the hash only once the document it evaluates in is `index.html` (`ARM_EARLY` in `test/harness.cjs`), with a re-arm behind it that says when it fires. Letting the hook-less load finish first is no cure: on a fresh profile CDP key events then stop reaching the page (reproduced deterministically, Alt+P and Alt+O dead). After the fix, 6 runs alone and 12 in three parallel loops passed without a hang or a re-arm. Delete this file once a few full suites have run without a hook hang; the other faults below are separate.

- **Checkouts no longer collide (25 October 2026):** `connect()` takes its CDP port from the OS and tags each profile folder with its checkout (`testProfileDir`), as does the restart test. Count a hang seen after that as this fault, not a collision, unless it is `gmist-start-guard`, which needs gmist's own ports. `connect()` also switches the auto-refresh timer off unless a test passes `autoRefresh: true` (25 October 2026): a tick had been landing in `runner-query-order`'s counted window one run in five. Still to do: a test Electron exiting when its node test process has gone.
  - First hang since then: `runner-keys` in `C:\dev\TagFox` at about 10:00 on 25 October 2026, `readyState: complete` and `Hit debug scenario: 4` as before, while a full suite ran in `C:\dev\TagFox-runner` on its own ports and profiles. It passed alone straight after. So the hang survives the collision fix; load from a second suite is still a suspect.
  - Three more in `C:\dev\TagFox` between about 11:20 and 11:30 on 25 October 2026, all while the `runner` session's full suite ran in `C:\dev\TagFox-runner`: a one-off probe, `runner-viewer-split` and `viewer-runner`. Each showed `readyState: complete` with an href carrying no `#tagfoxtest` hash, and `Hit debug scenario: 4` every five seconds, and each passed when rerun straight after. Whether a passing start also loses the hash from the href is not yet checked, so the missing hash is not yet evidence.
- Seen in four suite logs on 22 and 23 October 2026, then again in `tab lifecycle` on the run that tested runner commit `edabb5e`.
- **Two checkouts running the suite at once collide, and that looks like this fault.** Every checkout launches each test on the same CDP port and the same `%TEMP%\tagfox-test-*` profile folder, which `connect()` wipes at launch; only the leftover-process kill in `test-processes.cjs` is per checkout. On 24 October 2026 a suite in `C:\dev\TagFox-runner` overlapped one in `C:\dev\TagFox` (started 14:31:18). The worktree's suite lost three tests to the 45-second hook wait (`runner tags`, `hidden title bar`, `gmist start guard`), each with `readyState: complete` and `ERROR:debug_utils.cc(14)] Hit debug scenario: 4` on stderr every five seconds. Its `fuzz seed 2024` lost its hook mid-run ("Cannot read properties of undefined (reading 'state')") at the moment the other suite started `fuzz seed 999` on the same port 9302 and profile. A worktree rerun of `fuzz seed 2024` then left that `fuzz seed 999` hung. All four passed when rerun alone. So before counting a hang as this fault, check whether another suite was running; giving each checkout its own ports and profile folders, or a lock that `run-all.cjs` waits on, would settle how much of the fault is left.
- **A stranded test Electron loaded the whole machine for over an hour (24 October 2026, evening).** A `runner-layout` run started alone in `C:\dev\TagFox` at 21:45:57, seconds before a full suite in `C:\dev\TagFox-runner`, and the two shared port 9316 and the `tagfox-test-runner` profile. The lone run hung with no deadline, since only `run-all.cjs` has one, and its Electron (PID 34276) kept auto-refreshing a Runner search every 5 seconds. Each refresh is five Everything queries, so Everything (which answers one query at a time) ran at 1.2 to 2.3 cores, and a search that finds nothing took about 3 seconds against about 2ms earlier. That failed 7 of 30 runs in the worktree's suite on unchanged code, including commits that had passed it hours before. Three harness fixes would each have stopped it: per-checkout ports and profiles (above); `connect()` switching auto-refresh off unless a test asks for it; and a test Electron exiting when its node test process has gone (main polling its parent's PID under `TAGFOX_TEST_HIDDEN`). Until then, run a single test file under `timeout 300` and check for another suite first.
- **Four checks that fail on old code while Everything is slow (24 October 2026, near midnight).** With only about 1GB of RAM free, Everything's index was paged out and a search that finds nothing took 1.7s with Everything idle. These failed alone, and failed the same way on commits that had passed the suite hours earlier (`1c8862f`, `1c66612`), so they are tests that only a slow Everything exposes:
  - `refresh visibility`: after the click and after F5 the status reads "60 hits" instead of the "Refreshed …" report, so a later search (probably Smart's narrow or probe) is writing the hits line over the report.
  - `runner tags`: "removing it with the chip's x renames it back to beta.txt" and "adding LATER renames both files on disk".
  - `gmist start guard`: "sidecar port held" took 8.7 to 9.5s against its 8s budget.
  - Once the machine had recovered, the `refresh visibility` and `runner tags` checks passed alone again (runner session, just after midnight), which fits a slow Everything rather than a fault in the code. A fourth, in `runner keys`, was a race in the test and is fixed (`8676140`).
- `gmist start guard` failed once more under suite load on 25 October 2026 (stage eleven's run in `C:\dev\TagFox-runner`): its fake sidecar took more than 4s to bind 5199, with nothing else holding the port, and it passed alone straight after. Its budgets are the likeliest fault, as with the 8s one above.
- Two more one-offs in stage thirteen's suite (25 October 2026, `C:\dev\TagFox-runner`), both passing alone afterwards with no test Electron left: `viewer in runner` failed "closes the box" after a Quick TODO save, and `fuzz seed 2024` passed but left a test Electron that the harness had to stop.
- **Not every hang is a collision.** Later on 24 October 2026, with no other suite running (the `runner` session confirmed it was idle), `hover preview` lost its hook the same way in a full suite in `C:\dev\TagFox` and passed when rerun alone straight after.
- **A bad suite run with nothing else running (24 October 2026, testing the Runner breadcrumb).** 8 of 28 runs failed in one full suite in `C:\dev\TagFox`, with the `runner` session idle: `load-more regression` and `zoom buttons` lost their hooks (`Hit debug scenario: 4` again), `smoke`, `crud tab-isolation`, `column resize`, `splitter drag` and `zoom buttons` left an Electron running, `refresh visibility` failed with an empty `FAIL:`, and `hover preview` lost its two Classic icon checks. All eight passed when rerun one at a time straight after, leaving no test Electron behind. Steve's own TagFox was reloading its window during the run, since its renderer files were being edited; whether that matters is not known.
- It predates the Runner ProgramData change, so treat it as a harness fault rather than a product one.
- Start from the diagnostics the 45-second wait already prints, and find out whether the renderer is hung or never loaded `renderer.js`.
- A second harness fault may share the cause: a test that passed sometimes leaves its Electron main process running 1.5 seconds after the test exits, though `close()` sends it SIGKILL, so `run-all.cjs` fails the run with "LEFT RUNNING". Seen twice in 13 runs on 23 October 2026 (`tab lifecycle` in a full suite, `refresh visibility` alone); four further runs that listed test Electrons at 1.5, 5 and 12 seconds found none, so whether the process ever exits by itself is still open.
- `markdown preview never writes` failed "closing the editor saves the edit" once in a full suite in `C:\dev\TagFox-runner` with nothing else running (24 October 2026, evening). It left its Electron running too, then passed three times alone straight after. The check reads the disk 200ms after closing the editor, which is the likeliest cause.
- `hover preview` fails its two Classic icon checks ("resting on the row's icon opens the preview", "a repaint that removes the row under the open preview closes it") about one run in three, alone or in the suite (23 October 2026, at `f35c706`). A timing assumption in the test is the likeliest cause.
- Run from a checkout under `.claude\worktrees\` (where a background agent's worktree lands), `runner layout`, `runner keys`, `runner syntax` and `hover preview` fail on unchanged code, and pass from `C:\dev\TagFox`. Runner hides paths with a `.` segment, which probably hides the tests' own files there. Either the tests should not depend on the checkout's path, or agent worktrees should sit elsewhere.
